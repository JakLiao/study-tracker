# 服务启动顺序与自愈机制

> 场景：Docker Desktop 开机慢，或容器重启，数据库比 Web 服务晚就绪
> 结论：**服务会自己等数据库，不需要人工干预**
> 落地日期：2026-11-01

---

## 0. 一句话

服务启动时**先等 PostgreSQL 就绪再起 uvicorn**，等待期间进程一直活着；数据库一通就自动开始服务。

不要改成"崩了让守护进程重启"——那条路实测会**永久躺平**。

---

## 1. 故障现象（2026-11-01 实际发生）

Docker Desktop 启动后，容器 `study-pg` 状态是 `Up`，但：

```bash
curl http://127.0.0.1:5434   # 连接被拒
pm2 list | grep study-tracker
# study-tracker | errored | ↺ 15 | pid=0
```

PM2 里这个进程**连续崩了 15 次后彻底躺平**，即使数据库后来完全正常，也不会自己起来。必须人工 `pm2 restart study-tracker`。

容器日志时间是 `00:53:25 UTC`，而我 08:55 去看时 PM2 仍是 `errored/pid=0`——**中间那两分钟它一次都没再试过**。

---

## 2. 根因：不是"docker 启动慢"，是三件事叠加

### 2.1 应用在 import 期硬崩

`app/main.py`：

```python
app = create_app()      # 模块导入时执行
    └─ create_app()
         └─ init_db()   # 连不上数据库直接抛异常
```

连接被拒是**瞬时**的 → 进程 1 秒内就死。不是"连不上就重试"，是"连不上就死"。

### 2.2 PM2 的重启预算 2 秒烧光

PM2 默认 `max_restarts=15` / `restart_delay=0`。受控实验（脚本在标志文件缺失时立即退出）：

```
t= 2s  status=errored  restart_time=15  pid=0
```

**15 次重试在 2 秒内全部用完。**

### 2.3 烧满后 PM2 永久放弃

根因修好后继续观察 15 秒：`restart_time` 纹丝不动、`pid` 一直是 0。**一次都没再试过。**

---

## 3. 关键机制：`min_uptime` 才是"会不会放弃"的开关

PM2 判定一次重启算不算"成功"，看进程活了多久是否超过 `min_uptime`（默认 1000ms）：

| 情况 | `min_uptime` 判定 | 结果 |
|---|---|---|
| 进程 1 秒内死 | 算"不稳定重启" | 计数累加 → 15 次后**永久放弃** |
| 进程活过 `min_uptime` | 算"这次重启成功" | 计数清零 → **永远不会放弃** |

第二个实验（进程活 3 秒后才失败，超过默认 1s）：

```
t= 4s  status=online  restart_time=1  unstable_restarts=0
t=24s  status=online  restart_time=8  unstable_restarts=0
```

`restart_time` 一路涨到 8 却始终 `online` —— 因为每次都算"成功"，计数每次清零。

**study-tracker 恰好落在最坏的一格**：连接被拒是瞬间的，所以它永远活不过 1 秒，永远算"不稳定重启"。

> 推论：**让进程"活着等数据库"，比让它"崩了等重启"可靠得多。**

---

## 4. 落地的三层

### ① 启动时等数据库（`scripts/wait_for_db.py` + `pm2-start.sh` / `run.sh`）

`pm2-start.sh` 在 `exec uvicorn` 之前先等数据库就绪，期间进程一直活着 → 永远走不到重启路径。

探测分**两层**，因为两种失败处理方式相反：

| 情况 | 判定 | 处理 |
|---|---|---|
| TCP 端口不通（容器没起 / 端口没发布） | `not_listening` | 值得等 |
| 端口通但连不上（密码错 / 库名错） | `config_error` | 等也没用，**立刻报错** |

> 为什么必须分两层：psycopg 3.3 不透传连接失败的 SQLSTATE（密码错和端口拒连都是 `OperationalError`），只能靠先探 TCP 端口来区分。

超时后给出**可操作的排查清单**（容器在不在 → 端口发布没 → 端口通不通 → `.env` 连接串），而不是一坨 traceback。

### ② PM2 契约参数进版本库（`ecosystem.config.js`）

```js
max_restarts: 50,                  // 默认 15: 烧光后永久放弃
restart_delay: 5000,               // 默认 0: 失败后立刻重试, 等于几秒撞光预算
exp_backoff_restart_delay: 30000,  // 连续失败延迟翻倍, 封顶 30s
min_uptime: 10000,                 // 默认 1s: "假活"也算失败
```

**为什么必须进版本库**：这些参数决定"数据库晚启动时服务能不能自愈"，属于服务契约。只写在命令行就只活在某个人的 shell 历史里——而这个项目是个人业余维护，最怕"只有原作者知道为什么这么配"。

### ③ 应用层有限重试（`app/db.py`）

`init_db()` 连接失败时按指数退避重试（默认 5 次，共约 15s），给瞬时抖动留余地；超过仍失败才报错。**密码错这类配置问题立即失败，不浪费时间重试。**

### ④ 容器 healthcheck（`docker run --health-cmd`）

容器 "Up" **不代表**数据库能连：Docker 抢不到宿主端口时会静默丢弃端口发布，容器照样 Up 但连不上（§1 那次故障的现场之一）。healthcheck 让 `docker ps` 直接显示 `healthy` / `unhealthy`，不用再靠猜。

```bash
--health-cmd="pg_isready -U study -d study_tracker" \
--health-interval=5s --health-timeout=3s --health-retries=5 \
--health-start-period=10s
```

`--health-start-period` 不能省：PG 启动初期会短暂拒连，没有这段宽限期会被误判成 unhealthy。

> 改容器配置只能重建（Docker 不给已有容器加参数）。数据在具名卷 `study-pg-data` 里，**重建不碰卷**，但重建前务必先备份 + 重建后核对指纹（见 §5.3）。

## 5. 实测验证（2026-11-01）

### 5.1 四条探测路径

| 场景 | 期望 | 实测 |
|---|---|---|
| 数据库正常 | 立即放行 | exit 0，0s ✓ |
| 端口不通 | 等待后超时 | 持续 `[WAIT]`，超时 exit 1 + 排查清单 ✓ |
| 密码错 | 立即失败不等待 | exit 2，1s ✓ |
| `init_db()` 端口不通 | 指数退避重试 | 3 次尝试耗时 1.5s（0.5+1.0），抛可操作错误 ✓ |
| `init_db()` 密码错 | 立即失败 | 0.0s，不重试 ✓ |

### 5.2 端到端：停库 → 启库

```bash
docker stop study-pg
pm2 restart study-tracker
# 观察 18s: status=online, restart_time=1, pid=23285 (pid 不变, 计数不涨)
docker start study-pg
# 观察: pid 仍是 23285, 自动开始服务, health.db_ok=true
```

等待过程日志：

```
[WAIT] 数据库还没起来 (127.0.0.1:5434 连不上 (Connection refused)), 113s 后放弃 ...
[WAIT] 数据库还没起来 (127.0.0.1:5434 连不上 (Connection refused)), 107s 后放弃 ...
...
2026-11-01 10:16:16 INFO:     Application startup complete.
2026-11-01 10:16:16 INFO:     Uvicorn running on http://127.0.0.1:8876
```

**同一个进程扛过了数据库的整个不可用窗口，数据库一恢复就自动开始服务，零人工干预。**

对比修复前：2 秒内烧光 15 次重启 → `errored` → `pid=0` → 永久躺平 → 必须人工重启。

### 5.3 容器重建加 healthcheck（数据零丢失）

Docker 不能给已有容器加参数，要加 healthcheck 只能重建。数据在具名卷 `study-pg-data` 里，**重建不碰卷**，但仍按"先备份、再核对、最后才删旧容器"的顺序做：

| 步骤 | 结果 |
|---|---|
| 1. `pg_dump -Fc` 备份 `study_tracker` + `study_tracker_test` | 68K / 42K |
| 2. **还原验证**（备份本身可用） | 还原到临时库，9 张表行数全对，`assignments` / `completion_logs` 的 md5 与原库**逐字节一致** |
| 3. 存档容器规格（`docker inspect`） | image / env / 端口绑定 / 卷挂载 / 重启策略全部记下 |
| 4. 取数据基线指纹 | `schema_version=4`；assignments 217 行 md5=`67384d4a…`；completion_logs 548 行 md5=`2fa156de…` |
| 5. 停服务 → 停容器 → **改名保留**（回滚路径）→ 用同卷同规格重建 + healthcheck | 端口正常发布，health 转 `healthy` |
| 6. 重建后核对 | 行数全对，**两个 md5 与基线完全一致** |
| 7. 删旧容器 | `docker rm study-pg-old` |

重建后：

```
study-pg | Up 19 seconds (healthy) | 127.0.0.1:5434->5432/tcp
```

服务健康检查 `{"status":"ok","ai_reachable":true,"db_ok":true}`，看板读出今天的真实作业。

## 6. 排障速查

| 症状 | 处理 |
|---|---|
| 启动报"数据库未就绪" | 服务会自己等 `DB_WAIT_SECONDS` 秒（默认 120）；仍失败按提示逐条查 |
| `docker ps` 显示容器在跑但连不上 | 看 healthcheck 那一列。`unhealthy`/`starting` 很久 = 数据库真没就绪；显示 `healthy` 却连不上 = **端口没发布**：`docker inspect -f '{{json .NetworkSettings.Ports}}' study-pg`，是 `{}` 或只有 `{"5432/tcp":[]}` 就是没发布 → `docker restart study-pg` |
| PM2 显示 `errored` | PM2 烧光预算后不会自己再试 → `pm2 restart study-tracker`，再用 `pm2 logs study-tracker --err` 看当时为什么退出 |
| 要改容器参数（加 healthcheck 等） | 必须重建，数据在具名卷 `study-pg-data` 里不受影响；**先 `pg_dump` 备份 → 保留旧容器改名作回滚 → 重建 → 核对行数与 md5 指纹 → 才删旧容器**（§5.3 是完整流程） |

> 端口发布的坑另有一层：Docker 抢不到宿主端口时会**静默丢弃发布**，不报错、`docker ps` 也不显示映射。判断依据是 `NetworkSettings.Ports`（运行时真相），不是 `HostConfig.PortBindings`（只是请求）。
